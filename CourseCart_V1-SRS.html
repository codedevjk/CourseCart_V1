CourseCart

Brownfield Capstone Project SRS
Author : Jagmohan Kushwaha

1. Project Overview

CourseCart is a modern, full-stack learning management application designed to streamline the process of discovering, purchasing, and managing educational courses. It provides an end-to-end digital platform enabling customers to securely register, browse courses across categories, view detailed syllabuses, simulate purchases for immediate enrollment, and access lesson content while tracking their progress.

The application strictly enforces role-based workflows for two primary user types:

  • Customers (USER): Can register, log in, browse the active course catalog, purchase single courses via simulated checkout, access purchased course content (lessons), track progress per lesson, and view their order history.
  • Administrators (ADMIN): Can log in, manage categories and courses, manage course lifecycle (Draft, Active, Inactive), manage text-based course lessons, and view basic platform reporting metrics globally.

The project is built as a microservices-based architecture using Java 21, Spring Boot, Spring Cloud, and Angular — demonstrating modern enterprise development practices at a capstone-level of complexity.

2. System Architecture

The solution follows a Microservices Architecture consisting of four business services: User Service, Catalog Service, Commerce Service, and Enrollment Service, with communication managed through Spring Cloud Gateway and Spring Cloud Consul. All frontend requests must pass through the API Gateway.

2.2 Authentication & Authorization Design

Important: CourseCart utilizes a Frontend-Managed Identity Design. Identity (Username and Role) is managed in Angular `sessionStorage` (clears automatically on browser/tab close). No JWTs, Spring Security, or HTTP Interceptors are used to pass headers. Usernames/IDs are passed as standard explicit API parameters where required.

3. Getting Started

3.1 Setup Steps

  1. Start Consul for service discovery: consul agent -dev
  2. Ensure MySQL is running on port 3306.
  3. Initialize the databases by running the consolidated SQL scripts from the src/main/resources folder of each microservice:
    mysql -u root -p < backend/user-service/src/main/resources/user_db.sql
    mysql -u root -p < backend/catalog-service/src/main/resources/catalog_db.sql
    mysql -u root -p < backend/commerce-service/src/main/resources/commerce_db.sql
    mysql -u root -p < backend/enrollment-service/src/main/resources/enrollment_db.sql
  4. Start each backend microservice in separate terminals:
    cd backend/api-gateway && mvn spring-boot:run
    cd backend/user-service && mvn spring-boot:run
    cd backend/catalog-service && mvn spring-boot:run
    cd backend/enrollment-service && mvn spring-boot:run
    cd backend/commerce-service && mvn spring-boot:run
  5. Start the Angular application: run npm install then ng serve from frontend/coursecart-ui/.
  6. Open http://localhost:4200.

US 01 – User Registration

Priority: Must Have Primary Microservice: User Service

Acceptance Criteria

  • As an anonymous visitor, I want to securely register so that I can access the CourseCart platform and purchase courses.
  • Customers shall be able to register using their Full Name, Username, and Password.
  • Usernames shall be unique across the system.
  • Duplicate username registrations shall not be allowed; the system must return a clear validation message.
  • Newly registered users shall automatically be assigned a standard customer role.
  • Mandatory fields shall be validated before registration (e.g., minimum lengths, no empty strings).
  • Appropriate success, validation, and error messages shall be displayed clearly to the user.
  • The registration form must provide immediate input validation and smoothly redirect the user to the login page upon successful registration.

US 02 – User Login

Priority: Must Have Primary Microservice: User Service

Acceptance Criteria

  • As a registered user, I want to log in so that I can access the application based on my assigned role.
  • Users shall be able to log in using their Username and Password.
  • Authentication shall securely validate credentials against stored records.
  • The user's access level and role shall be identified during a successful login.
  • Identity and session information shall be stored securely for the duration of the visit and cleared automatically when the browser or tab is closed.
  • Upon successful login, standard users shall be directed to the course catalog or their learning area, while administrators shall be directed to the management dashboard.
  • Users shall be able to log out securely, which immediately clears their active session.
  • Mandatory fields shall be validated before attempting to log in.
  • Appropriate error messages (e.g., 'Invalid credentials') shall be displayed for failed attempts.

US 03 – View Profile Trainee Task

Priority: Must Have Primary Microservice: User Service

Acceptance Criteria

  • As a logged-in user, I want to view my basic profile details, so that I can verify my account information.
  • The system shall display the user's name and username securely.
  • Profile data shall be retrieved securely using the logged-in user's identity.
  • The user interface must provide a clean and intuitive view representing the user's identity and details.

US 04 – Admin Category Management Trainee Task

Priority: Must Have Primary Microservice: Catalog Service

Acceptance Criteria

  • As an admin, I want to manage course categories, so that I can organize the catalog.
  • Administrators can view a paginated or structured list of all categories.
  • Administrators can create a new category by providing a unique name.
  • Administrators can edit the name of an existing category.
  • Administrators can attempt to delete a category.
  • A category cannot be deleted if there are active courses currently assigned to it.
  • If a deletion is prevented, the system must gracefully handle the rejection and display a user-friendly error message explaining the reason.

US 05 – Admin Course Management Trainee Task

Priority: Must Have Primary Microservice: Catalog Service

Acceptance Criteria

  • As an admin, I want to manage course metadata, so that I can define what is sold on the platform.
  • Administrators can view all courses regardless of their current publishing status.
  • Administrators can create and edit courses by providing a Title, Description, Price, and Category.
  • Every course must be assigned to exactly one existing category.
  • Administrators can set a fixed price for the course, including setting it to free.
  • Newly created courses shall default to a 'Draft' status.
  • The system must validate that the price is not negative and that all required fields are provided before saving.
  • Administrators can delete a course. Deleting a course must also securely remove all of its associated lessons.

US 06 – Admin Lesson Management

Priority: Must Have Primary Microservice: Catalog Service

Acceptance Criteria

  • As an admin, I want to manage lessons within a course, so that I can build the educational content.
  • Administrators can navigate into a specific course to manage its associated lessons.
  • Administrators can create a text-based lesson with a Title and Content for a course.
  • Administrators can edit existing lesson titles and their text content.
  • Administrators can completely delete a lesson from a course.
  • Deleting a lesson must be handled gracefully so that it does not corrupt or break the learning progress records of users currently enrolled in the course.

US 07 – Admin Course Lifecycle Management Trainee Task

Priority: Must Have Primary Microservice: Catalog Service

Acceptance Criteria

  • As an admin, I want to toggle a course's status between Draft, Active, and Inactive, so that I can control its public availability.
  • Course publishing statuses are strictly limited to Draft, Active, or Inactive.
  • Administrators can change a Draft course to Active to publish it to the public catalog.
  • Administrators can change an Active course to Inactive to retire it from future sales.
  • Inactive courses must immediately be hidden from the public catalog for new customers.
  • Changing a course's status to Inactive must not affect previously enrolled users; they must retain full access to the course in their learning dashboard.

US 08 – Browse and Search Catalog Trainee Task

Priority: Must Have Primary Microservice: Catalog Service

Acceptance Criteria

  • As a user, I want to browse and search the active course catalog, so that I can find courses to learn.
  • The system shall display a visual grid or list containing only Active courses.
  • Users can filter the catalog by selecting a specific category.
  • Users can search for courses by entering part or all of a Course Title.
  • The catalog must support structured pagination to cleanly display a set number of courses per page.
  • Each course card shall display the Title, Price, and Category name clearly.
  • The interface must provide clear visual feedback during loading times and display helpful messages if no courses match the search criteria.

US 09 – View Course Details Trainee Task

Priority: Must Have Primary Microservice: Catalog Service

Acceptance Criteria

  • As a user, I want to view detailed information about a course, so that I can decide whether to purchase it.
  • The system shall display the course Title, Description, Category, and Price in a detailed view.
  • The system shall display a read-only list of the course syllabus (Lesson titles).
  • If the user is logged in and not yet enrolled, a clear option to purchase the course is displayed.
  • If the user is logged in and already enrolled, an option to directly navigate to the course material is displayed.
  • If the visitor is not logged in, they are prompted to log in or register before they can purchase the course.

US 10 – Single Course Purchase (Mock Checkout) Trainee Task

Priority: Must Have Primary Microservice: Commerce Service

Acceptance Criteria

  • As a user, I want to purchase a course through a simulated checkout, so that I can gain access to its content.
  • Initiating a purchase directs the user to a streamlined mock checkout flow.
  • The system shall clearly display the course details and the total price to be paid.
  • The user can select a simulated payment method, and the system simulates a successful transaction.
  • The system must strictly prevent duplicate purchases if the user is already enrolled in the course.
  • Upon a successful transaction, the system records the order and officially enrolls the user in the course.
  • Failed transaction attempts must not grant course access or create order records.
  • The user is seamlessly redirected to a success screen or their learning dashboard upon completion.

US 11 – View Order History Trainee Task

Priority: Must Have Primary Microservice: Commerce Service

Acceptance Criteria

  • As a user, I want to view my past successful purchases, so that I have a record of my transactions.
  • The system shall display a clear, tabular list of the user's successfully completed orders.
  • The history must display the Course Title, Order Date, and Total Price Paid for each transaction.
  • Failed or incomplete purchase attempts must not appear in this history.
  • The order history must be sorted chronologically, showing the most recent transactions first.

US 12 – My Learning Dashboard

Priority: Must Have Primary Microservice: Enrollment Service

Acceptance Criteria

  • As a user, I want to see a list of all courses I am enrolled in, so that I can resume learning.
  • The system shall display a personalized dashboard of all courses the user is enrolled in, including any courses that have since been retired by administrators.
  • The system shall automatically calculate and display the user's overall progress percentage for each course.
  • The dashboard must display a welcoming and helpful message if the user has not yet enrolled in any courses.

US 13 – Access Course Content

Priority: Must Have Primary Microservice: Enrollment Service

Acceptance Criteria

  • As an enrolled user, I want to read the lessons of a course, so that I can learn the material.
  • Enrolled users can navigate into a course to view the full syllabus and access lesson materials.
  • Users can comfortably view the text-based educational content of any selected lesson.
  • The system must strictly deny access and gracefully redirect any non-enrolled user attempting to view restricted lesson content directly.

US 14 – Track Lesson Progress

Priority: Must Have Primary Microservice: Enrollment Service

Acceptance Criteria

  • As an enrolled user, I want to mark lessons as complete, so that my overall course progress is updated.
  • Users can manually toggle a lesson's status between Complete and Incomplete.
  • Toggling a lesson's status immediately and securely saves the user's progress.
  • The course's overall progress percentage is recalculated and updated dynamically on the screen in real-time.

US 15 – Admin Dashboard

Acceptance Criteria

  • The system shall display the total count of registered users on the platform.
  • The system shall display the total count of published, active courses.
  • The system shall display the total number of course enrollments.
  • The system shall display the total aggregated revenue from all successful transactions.
  • These performance metrics must be gathered efficiently and displayed clearly in dashboard summaries.
  • The dashboard shall also display a list of recent transactions for administrative reference.

5. Data Persistence Rules

The application shall use four separate MySQL databases — one per microservice — as the permanent storage for all business data: coursecart_user_db, coursecart_catalog_db, coursecart_commerce_db, and coursecart_enrollment_db. No cross-service database joins are permitted; all cross-service data access is done through REST API calls.

  • All successful Create, Update, and Delete operations shall be immediately persisted in the database.
  • All View and Search operations shall always retrieve the latest persisted records.
  • Changes performed by one module shall be immediately reflected wherever the same data is consumed.
  • No business data shall be maintained only in frontend memory; frontend sessionStorage is strictly reserved (clears on tab close) for managing active session state (user info and role).
  • Data shall remain available after browser closure, frontend restart, backend restart, application restart, or system reboot. ddl-auto: update ensures no data loss on restart; *.sql files are one-time setup, do not re-run
  • The database shall always be considered the single source of truth for all business operations.

10. Implementation Guidelines

10.1 General Coding Practices

  • Use Lombok to generate boilerplate code (e.g., @Data, @NoArgsConstructor) for all model classes. Prefer constructor injection for dependency management.
  • Implement logic using Lambdas and Streams.
  • Organize code into logical layers (Controller, Service, Repository, DTO, Entity, Configuration, etc.).
  • Use meaningful package names reflecting the domain.
  • Employ Spring Dependency Injection for effective component management.

10.2 Error Handling

  • Handle cases where the user attempts to access resources without authorization.
  • Implement custom exceptions with user-friendly error messages.
  • Use a centralized exception handling mechanism to translate exceptions into appropriate HTTP responses.
  • Use @RestControllerAdvice (GlobalExceptionHandler) to intercept, format, and log all service exceptions.
  • Return meaningful success and error responses with appropriate HTTP status codes.

10.3 DTOs and Mapping

  • Data Transfer Objects (DTOs) must be used for all API request and response payloads.
  • Database Entities shall NEVER be exposed directly through REST APIs.
  • Use ModelMapper (configured as a Spring @Bean in each service) for DTO/Entity conversions. Add explicit mappings for any fields that do not auto-map by convention.

10.4 Database Interaction

  • Spring Data JPA Repositories must be used for all database operations and query generation.
  • Configure appropriate database properties and table generation strategies (spring.jpa.hibernate.ddl-auto=update is used here to ensure schema synchronization).

10.5 API Design

  • All APIs should be mapped with an appropriate base URI representing the resource collection (e.g., /api/courses).
  • Ensure strict isolation of server port numbers for each microservice (e.g., Gateway: 8080, User: 8081, Catalog: 8082, Commerce: 8084, Enrollment: 8083).
  • Use appropriate HTTP methods (GET, POST, PUT, DELETE, PATCH) and let Spring automatically resolve appropriate status codes.

10.6 Microservice Communication

  • Register all microservices with Spring Cloud Consul for dynamic service discovery and health monitoring.
  • Route all frontend and external client requests exclusively through the Spring Cloud Gateway.
  • Use WebClient (from Spring WebFlux) for inter-service HTTP communication. The @LoadBalanced WebClient.Builder bean enables load-balanced calls using Consul service names (e.g., http://catalog-service). Do NOT use the deprecated RestTemplate.
  • Implement Spring Cloud Circuit Breaker (Resilience4j) for inter-service calls using the following precise configuration:
    • slidingWindowSize: 10 (Evaluates the last 10 calls)
    • failureRateThreshold: 50% (Opens the circuit if 50% of calls fail)
    • waitDurationInOpenState: 60 seconds (Time before transitioning to half-open state)
    • permittedNumberOfCallsInHalfOpenState: 3
    • All circuit breaker configuration must be defined in application.yml under resilience4j.circuitbreaker.instances.
    • Define appropriate @CircuitBreaker fallback methods to ensure graceful degradation.
  • All services must use application.yml for all configuration (not application.properties).

10.7 Validation

  • Bean Validation should be used for all user inputs.
  • Custom Validators should be implemented for complex validations.
  • All request parameters must be validated for null or empty values. Return standard Bean Validation error messages.

10.8 Testing

  • Write unit test cases for critical service methods using JUnit and Mockito.
  • Achieve a minimum of 80% code coverage.
  • Test all REST APIs using Postman or Swagger/OpenAPI.
